Харків – 2026
     1. Мета роботи
     Ознайомитися з методами та інструментами масштабування серверної частини програмної системи для роботи в умовах високого навантаження. Практично реалізувати горизонтальне масштабування бекенду, налаштувати балансувальник навантаження та провести навантажувальне тестування системи для аналізу залежності пропускної здатності від кількості серверів.
     2. Завдання
     Обрати стратегію масштабування (в цьому випадку горизонтальне масштабування серверів); виконати розгортання кластера локально за допомогою технологій контейнеризації; налаштувати балансування трафіку між декількома екземплярами сервера; провести навантажувальне тестування за допомогою інструменту Locust, порівняти показники системи.
     3. Опис виконаної роботи
     3.1. Опис стратегії масштабування системи
     Для системи ClimaFlow, метої якої є обробка інтенсивного потоку телеметрії від багатьох IoT-пристроїв, було обрано стратегію горизонтального масштабування для серверної частини.
     Суть стратегії полягає в тому, що замість збільшення обчислювальної потужності одного сервера (вертикальне масштабування), ми додаємо нові ідентичні копії серверного застосунку. Ця стратегія ідеально підходить для нашого бекенду на базі ASP.NET Core, оскільки він побудований за архітектурним стилем REST і є stateless (не зберігає стан клієнта в оперативній пам'яті). Кожен IoT-пристрій відправляє HTTP POST-запит, який може бути оброблений будь-якою з доступних копій сервера незалежно від інших.
     3.2. Опис технічних рішень, які роблять масштабування можливим
     3.2.1. Контейнеризація (Docker)
     Серверний застосунок запаковано у легкопереносимий Docker-образ (на базі mcr.microsoft.com/dotnet/aspnet:8.0). Це робить запуск нових копій сервера питанням кількох секунд, адже не потрібно налаштовувати середовище на хост-машині.

     3.2.2. Оркестрація (Docker Compose)
     Управління кластером описано декларативно у файлі docker-compose.yml. Динамічне розгортання додаткових копій сервера виконується за допомогою вбудованого механізму масштабування deploy: replicas (або командою --scale climaflow-api=N) (знизу наведений код docker-compose.yml).
      version: '3.8'
      
      services:
        sqlserver:
          image: mcr.microsoft.com/mssql/server:2022-latest
          environment:
            - ACCEPT_EULA=Y
            - MSSQL_SA_PASSWORD=ClimaFlow_StrongPass1!
          ports:
            - "1433:1433"
          healthcheck:
            test: ["CMD", "/opt/mssql-tools18/bin/sqlcmd", "-C", "-U", "sa", "-P", "ClimaFlow_StrongPass1!", "-Q", "SELECT 1"]
            interval: 10s
            timeout: 10s
            retries: 10
            start_period: 15s
          deploy:
            resources:
              limits:
                cpus: '3.0'
                memory: 4G
      
        climaflow-api:
          build: .
          depends_on:
            sqlserver:
              condition: service_healthy
          environment:
            - "ConnectionStrings__DefaultConnection=Server=sqlserver;Database=ClimaFlowDb;User Id=sa;Password=ClimaFlow_StrongPass1!;TrustServerCertificate=True;MultipleActiveResultSets=true"
          deploy:
            replicas: 10
            resources:
              limits:
                cpus: '0.3'
                memory: 256M
      
      
        nginx:
          image: nginx:latest
          volumes:
            - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
          ports:
            - "8080:80"
          depends_on:
            - climaflow-api
     3.2.3. Балансувальник навантаження (Nginx Load Balancer) 
     Оскільки ми маємо декілька копій API, IoT-пристроям потрібна єдина точка входу. Для цього розгорнуто контейнер Nginx у режимі Reverse Proxy. Він приймає всі запити на порт 8080 і рівномірно розкидає їх між поточними активними контейнерами climaflow-api (знизу наведений код nginx.conf).
      events { worker_connections 1024; }
      
      http {
          server {
              listen 80;
      
              resolver 127.0.0.11 valid=5s;
      
              location / {
                  set $backend "http://climaflow-api:8080";
      
                  proxy_pass $backend;
                  
                  proxy_set_header Host $host;
                  proxy_set_header X-Real-IP $remote_addr;
                  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
              }
          }
      }
     3.2.4. Автоматичні міграції БД 
     Для забезпечення автономності кластера, при старті C#-сервер виконує команду dbContext.Database.Migrate(), автоматично створюючи та налаштовуючи структуру таблиць у контейнері з базою даних.
     3.3. Аналіз вузьких місць, а саме ресурсів, що вичерпуються першими
     Під час обробки великої кількості одночасних запитів, система стикається з обмеженнями апаратних ресурсів. У даній архітектурі вузькі місця виникають у такому порядку:
1. Процесорний час серверів API: прийом JSON-телеметрії, її десеріалізація, валідація бізнес-правил та маппінг об'єктів вимагають значних обчислень. Для симуляції цього вузького місця у docker-compose.yml було встановлено жорсткий ліміт ресурсів: cpus: '0.3' (копія сервера отримує лише 30% одного ядра процесора). При збільшенні потоку запитів, процесор швидко перевантажується, потоки стають у чергу, що викликає різке зростання часу відповіді.
2. Оперативна пам’ять бази даних: СУБД MS SQL Server агресивно кешує дані в оперативну пам'ять для прискорення доступу. При тисячах операцій INSERT на секунду (запис телеметрії та інцидентів), оперативна пам'ять може бути вичерпана. Щоб запобігти збою всієї системи, ресурси БД також обмежено (memory: 4G).
3. Пул підключень: при нестачі обчислювальних ресурсів бази даних, запити від API до БД починають затримуватися, що призводить до вичерпання ліміту відкритих TCP-з'єднань між бекендом та MS SQL Server.
3.4. Опис навантажувальних тестів
     Для перевірки ефективності масштабування було проведено навантажувальне тестування інструментом Locust (написаний мовою Python).
     Спочатку, було написано скрипт locustfile.py, що імітує поведінку 1000 IoT-пристроїв. При старті кожен пристрій генерує унікальну MAC-адресу та реєструється в системі. Після цього пристрої починають безперервно відправляти POST-запити з показниками мікроклімату (температура, вологість, CO₂) з інтервалом від 1 до 3 секунд на загальний Nginx Load Balancer (http://localhost:8080).
      from locust import HttpUser, task, between
      import random
      
      class IoTDeviceSimulator(HttpUser):
          host = "http://localhost:8080" 
          wait_time = between(1, 3) 
      
          def on_start(self):
              self.mac_address = f"MAC-{random.randint(1, 999999)}"
              
              self.client.post("/api/Devices", json={
                  "name": f"Simulated Sensor {self.mac_address}",
                  "macAddress": self.mac_address
              })
      
          @task
          def send_telemetry(self):
              payload = {
                  "macAddress": self.mac_address,
                  "temperature": round(random.uniform(18.0, 30.0), 1),
                  "humidity": round(random.uniform(30.0, 70.0), 1),
                  "co2Level": round(random.uniform(400, 1200), 1)
              }
              
              self.client.post("/api/Readings", json=payload)

     3.4.2. Навантаження з горизонтальне масштабуванням (15 екземплярів API)
     Не зупиняючи Locust, систему було масштабовано командою docker-compose up -d --scale climaflow-api=15. Nginx автоматично виявив 14 нових контейнерів і почав розподіляти між ними трафік.

     3.5. Висновки
     У ході виконання лабораторної роботи було практично доведено ефективність горизонтального масштабування. Використання Docker та Nginx дозволило динамічно керувати кількістю обчислювальних вузлів системи ClimaFlow. Аналіз навантажувальних тестів за допомогою Locust наочно продемонстрував, що при вичерпанні лімітів процесорного часу, додавання нових серверних реплік дозволяє миттєво зняти навантаження з вузьких місць, суттєво зменшити час відповіді сервера та збільшити кількість успішних запитів за секунду.
