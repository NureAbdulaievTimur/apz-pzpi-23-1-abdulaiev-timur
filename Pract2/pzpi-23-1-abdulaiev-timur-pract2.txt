     3 ОПИС ВИКОНАНОЇ РОБОТИ
     3.1 Загальні відомості про систему
     Назва системи: Стрімінгова платформа Twitch.
     Розробник: Twitch Interactive (дочірня компанія Amazon).
     Призначення системи:
     — область застосування: сфера цифрових розваг, кіберспорт, відеоблогінг, онлайн-навчання та спілкування в реальному часі;
     — користувачі: контент-мейкери (стрімери), глядачі, модератори спільнот, розробники сторонніх додатків;
     — основні функції: трансляція відео у реальному часі з наднизькою затримкою, забезпечення масового текстового спілкування (тобто чату), монетизація контенту, збереження записів трансляцій (VOD), автоматизована модерація та система рекомендацій контенту.
     3.2 Архітектурний стиль системи
     Система використовує гібридну мікросервісну архітектуру з подієво-орієнтованими компонентами та власною глобальною мережею доставки контенту.
     Обґрунтування вибору архітектури:
     Twitch одночасно обслуговує мільйони глядачів та приймає десятки тисяч вхідних відеопотоків. Монолітна архітектура не здатна впоратися з таким навантаженням. Мікросервісний підхід дозволяє незалежно масштабувати різні вузли: наприклад, сервіси чату (які генерують мільйони повідомлень на секунду) масштабуються окремо від систем бізнес-логіки (оплата підписок). Подієво-орієнтована модель ідеально підходить для архітектури реального часу (сповіщення про початок стріму, нові повідомлення в чаті). Власна CDN необхідна для уникнення буферизації відео та забезпечення мінімального пінгу між стрімером і глядачем у будь-якій точці світу.
     3.3 Основні компоненти системи
     Опис підсистем:
     1. Інтерфейс користувача (Frontend): Веб-додаток (побудований на React), мобільні додатки (iOS/Android), нативні додатки для ігрових консолей (PlayStation, Xbox) та Smart TV.
     2. Серверна частина (Backend - Video & Chat):
     — Video Ingest Servers: приймають вихідний потік від стрімера;
     — Transcoding System: розбиває потік на різні якості (1080p, 720p, 480p);
     — Chat Servers: високопродуктивні сервери на базі мови Go для обробки повідомлень.
     3. Рівень бізнес-логіки (Core API): Система авторизації (OAuth), сервіси управління профілями, система монетизації та обробки платежів, рушій рекомендацій на базі машинного навчання.
     4. Рівень зберігання даних:
     — PostgreSQL: для зберігання реляційних даних (профілі, налаштування);
     — Amazon S3: для зберігання масивів неструктурованих даних (записи трансляцій - VODs, кліпи);
     — Redis/Memcached: для кешування сесій та статусів "онлайн" у реальному часі.
5. Допоміжні сервіси: Система AutoMod (ШІ-модерація), EventSub (система вебхуків для розробників), сервіси аналітики трафіку.
     3.4 Взаємодія компонентів
Опис потоків даних, протоколів взаємодії, механізмів синхронізації:
     1. Відеопотік: стрімер відправляє відео через протокол RTMP або SRT на найближчий Ingest-сервер. Далі потік передається на транскодери. Готові відеофрагменти поширюються через Edge-сервери CDN до глядачів за протоколом HLS.
     2. Чат: взаємодія глядача з чатом відбувається через протокол WebSockets для забезпечення миттєвої доставки повідомлень без постійного опитування сервера.
     3. Синхронізація: для синхронізації відео та дій на екрані (наприклад, інтерактивні розширення Twitch Extensions) використовується протокол Pub/Sub та точні часові мітки, вбудовані у відеопотік.
     Нижче наведені UML-діаграми:
     
     
Рисунок 3.4.1 – UML-діаграма послідовності
     
     Діаграма послідовності (див. рис. 3.4.1) демонструє шлях сигналу: від ініціалізації з'єднання в OBS Studio (клієнт стрімера) через авторизацію ключа трансляції на серверах Twitch до розгалуження потоку на транскодері та його доставки кінцевому клієнту (браузеру глядача).
     
     
Рисунок 3.4.2 – UML-діаграма розгортання

     Діаграма розгортання (див. рис. 3.4.2) ілюструє географічний розподіл системи: балансувальники навантаження направляють трафік на найближчі периферійні вузли (Edge Nodes) в залежності від IP-адреси користувача, зменшуючи навантаження на центральні дата-центри AWS.
     3.5 Масштабованість та надійність
Система використовує наступні методи та технології:
     — механізми балансування навантаження: використовується DNS-маршрутизація (Amazon Route 53) та Anycast для направлення користувачів до географічно найближчого сервера. Внутрішнє балансування між мікросервісами забезпечується AWS Elastic Load Balancing;
     — відмовостійкість: архітектура передбачає graceful degradation (витончену деградацію). Якщо сервіс чату або система рекомендацій падає, трансляція відео все одно продовжує працювати без переривань;
     — кешування: жорстке кешування API-запитів, які часто повторюються за допомогою Redis. Відео-сегменти кешуються безпосередньо на Edge-серверах CDN;
     — реплікація: бази даних користувачів реплікуються у конфігурації Multi-AZ (у різних зонах доступності) для запобігання втраті даних;
     — контейнеризація або хмарна інфраструктура: уся сучасна інфраструктура Twitch працює в екосистемі Amazon Web Services (AWS) з використанням контейнеризації (Docker, Amazon ECS/EKS) для швидкого розгортання та масштабування сервісів чату і API під час пікових навантажень (наприклад, під час великих кіберспортивних турнірів).
     3.6 Приклади програмної реалізації
     1. Подієво-орієнтована архітектура, а саме обробка вебхуків через Twitch EventSub: замість того, щоб сторонні сервіси (наприклад, Discord-боти або оверлеї) постійно опитували API Twitch (Polling), Twitch використовує архітектуру Event-Driven. Коли відбувається подія (стрімер запускає ефір), Twitch сам надсилає POST-запит на зареєстрований сервер.
     2. Реалтайм-комунікація або підключення до серверів чату (TMI) через WebSockets: чат Twitch обробляє мільйони повідомлень. Для забезпечення доставки без затримок використовується протокол WebSockets поверх стандарту IRC.
     3. Зниження навантаження на БД, а саме патерн кешування (Redis Cache-Aside): коли глядач відкриває головну сторінку, Twitch потрібно показати статус тисяч каналів. Замість того, щоб звертатися до жорсткого диска бази даних PostgreSQL, система звертається до оперативної пам'яті (Redis).
     4. Клієнтська реалізація доставки відео HLS: frontend Twitch не отримує один цілісний відеофайл. Він завантажує маніфест (.m3u8), який вказує на короткі відеосегменти по 2 секунди.
     Весь код до цих пунктів наведений у додатку В.

ДОДАТОК В
Запити до ШІ

Запит: Як Twitch обробляє відео?
Відповідь: Twitch використовує складну, високооптимізовану систему для обробки відео в реальному часі. Головна мета цієї системи — прийняти відео від стримера, адаптувати його для різних пристроїв і швидкостей інтернету, а потім доставити мільйонам глядачів із мінімальною затримкою.
Весь процес можна розділити на кілька ключових етапів:
1. Передача потоку (Ingestion)
Стример використовує програму для трансляції (наприклад, OBS Studio, XSplit) для захоплення гри, камери та мікрофона.
• Протокол: Зібраний медіапотік зазвичай відправляється на найближчий сервер прийому Twitch (Ingest Server) за допомогою протоколу RTMP (Real-Time Messaging Protocol).
• Формат: Найчастіше використовується відеокодек H.264 (хоча Twitch також впроваджує новіші AV1 та VP9) і аудіокодек AAC.
2. Транскодування (Transcoding)
Це найважливіший і найбільш ресурсомісткий етап обробки. Коли сервери Twitch отримують оригінальний потік (Source), вони починають його "розщеплювати".
• Адаптивний бітрейт (ABR): Twitch створює кілька копій відео нижчої якості (наприклад, 720p60, 480p, 360p, 160p) з меншим бітрейтом. Це робиться для того, щоб глядачі з повільним інтернетом або на мобільних пристроях могли дивитися трансляцію без постійних буферизацій.
• Пріоритетність: Транскодування гарантовано надається Партнерам (Partners) Twitch. Афіліати (Affiliates) та звичайні стримери отримують ці варіанти якості лише тоді, коли на серверах Twitch є вільні обчислювальні потужності. Якщо потужностей не вистачає, глядачі зможуть дивитися стрім лише в оригінальній якості (Source).
3. Пакування та сегментування (Packaging)
Відео не передається глядачеві єдиним неперервним файлом.
• HLS (HTTP Live Streaming): Twitch використовує цей протокол для доставки відео. Оригінальний і транскодовані потоки нарізаються на короткі фрагменти (сегменти) тривалістю по 2-3 секунди.
• Низька затримка: Завдяки технології Low-Latency HLS (LL-HLS) Twitch вдається зменшити затримку між стримером і глядачем до 1-3 секунд, що критично важливо для інтерактивності в чаті.
4. Дистрибуція через CDN (Content Delivery Network)
Щоб відео не "гальмувало" через велику відстань між сервером і глядачем, Twitch використовує величезну мережу доставки контенту.
• Точки присутності (PoP): Сервери Twitch розташовані у великих містах та дата-центрах по всьому світу. Створені сегменти відео кешуються на цих вузлах.
• Коли ви відкриваєте стрім, ваш плеєр підключається до найближчого до вас сервера (наприклад, у Варшаві чи Франкфурті), а не до сервера в США, куди стрімить автор.
5. Відтворення у глядача (Playback)
Відеоплеєр Twitch (у браузері, на телефоні чи телевізорі) завантажує спеціальний файл-плейлист (m3u8), який вказує, де знаходяться сегменти відео.
• Плеєр постійно аналізує швидкість вашого інтернет-з'єднання. Якщо швидкість падає, він автоматично завантажує сегменти нижчої якості (наприклад, перемикається з 1080p на 480p), щоб відтворення не переривалося.
6. Збереження записів (VODs & Clips)
Паралельно з живою трансляцією Twitch зберігає отримані сегменти відео на серверах материнської компанії — Amazon Web Services (AWS) (зокрема в хмарних сховищах Amazon S3). Завдяки цьому, одразу після закінчення (або навіть під час) стріму відео стає доступним як запис (Video on Demand) і з нього можна створювати короткі кліпи.

Запит: Яка загальна архітектура Twitch'а?
Відповідь: Архітектура Twitch — це масштабна розподілена система, яка складається з безлічі незалежних сервісів. Головний виклик для Twitch полягає в тому, що їм потрібно одночасно підтримувати два гігантські, але принципово різні за своєю природою потоки даних: важке відео та легкі, але надзвичайно часті текстові повідомлення (чат).
Загалом систему можна розділити на кілька ключових підсистем:
1. Відео-інфраструктура (Video Pipeline)
Це ядро платформи, про яке ми частково говорили раніше. Ця система спроєктована для максимальної пропускної здатності (Bandwidth).
• Edge Ingest (Вузли прийому): Сервери по всьому світу, які приймають RTMP-потоки від стримерів.
• Transcoder Cluster: Кластери потужних серверів (переважно на базі AWS), які розкодовують відео, змінюють його роздільну здатність та пакують у формат HLS.
• CDN (Content Delivery Network): Twitch використовує гібридну модель. У них є власна глобальна мережа вузлів (Points of Presence) для доставки відео у густонаселених регіонах, а також вони використовують партнерські CDN (наприклад, Amazon CloudFront) для забезпечення глобального покриття.
2. Система чату (Twitch Messaging Interface - TMI)
Чат Twitch масштабується зовсім інакше, ніж відео. Тут головна проблема — кількість одночасних з'єднань і повідомлень на секунду (понад мільйони під час великих подій).
• Pub/Sub архітектура: Система працює за принципом "Видавець-Підписник". Коли користувач пише в чат, повідомлення публікується в певний "канал", і всі користувачі, підключені до цього каналу (підписники), отримують його.
• Протокол: Історично чат Twitch був побудований на старому протоколі IRC (Internet Relay Chat). Сьогодні він використовує кастомні рішення на базі WebSockets, але все ще підтримує IRC-команди для сумісності з тисячами ботів (Nightbot, Moobot тощо).
• Технології: Сервери чату написані переважно на Go (Golang) через його чудову здатність обробляти багато одночасних з'єднань із мінімальними затримками.
3. Бекенд-сервіси (Core Backend)
Це "мозок" платформи, який керує акаунтами, підписками, платежами, налаштуваннями каналів та бізнес-логікою.
• Мікросервісна архітектура: Колись Twitch був єдиним великим монолітним застосунком на Ruby on Rails. Зі зростанням платформи його розбили на сотні незалежних мікросервісів (більшість з яких зараз працюють на Go).
• API (GraphQL): Для зв'язку між фронтендом (сайтом/додатком) та бекендом Twitch активно використовує GraphQL. Це дозволяє клієнтам (наприклад, мобільному додатку) запитувати рівно ті дані, які їм потрібні в даний момент (наприклад, тільки назву стріму і кількість глядачів), не завантажуючи зайву інформацію.
4. Дані та Зберігання (Data Layer)
Для різних завдань Twitch використовує різні типи баз даних:
• Реляційні БД (PostgreSQL / Amazon Aurora): Для зберігання важливих транзакційних даних (інформація про користувачів, платежі, підписки).
• NoSQL (Amazon DynamoDB): Для даних, які потребують надшвидкого читання/запису у величезних масштабах (статуси онлайн/офлайн, історія лайків тощо).
• Кешування (Redis / Memcached): Використовується для зберігання тимчасових даних у пам'яті (наприклад, поточна кількість глядачів на стрімі), щоб не перевантажувати основні бази даних постійними запитами.
5. Пошук та Рекомендації (Discovery)
Щоб ви могли знайти нових стримерів, Twitch збирає величезну кількість аналітики:
• Аналітика даних: Події з плеєра, кліки та перегляди надсилаються у сховища даних (Data Lakes) на базі Amazon S3.
• Машинне навчання (AWS SageMaker): Алгоритми аналізують ці дані, щоб формувати персоналізовану стрічку рекомендацій на головній сторінці.
• Пошук: Для швидкого пошуку за назвами ігор чи нікнеймами використовується Elasticsearch (або аналоги, такі як Amazon OpenSearch).
Підсумовуючи: Twitch — це екосистема, де відео обробляється через власну інфраструктуру та CDN, чат працює як блискавична система повідомлень на базі Go, а вся бізнес-логіка, збереження даних та машинне навчання надійно спираються на хмарні потужності Amazon Web Services (AWS), яка володіє Twitch.
